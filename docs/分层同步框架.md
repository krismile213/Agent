# 分层同步框架：两次全量兜底 + 短时增量脉冲

> 2026-11-16 设计稿。参考了业界 hybrid（增量 + 周期全量对账）模式，
> 并结合钉钉 API 的实际能力和本机 5095 单实测数据裁剪。
> **本稿不改任何现有同步代码**，`approval_sync.py` / `daily_brief.py` / 数据后台均不动。

---

## 0. 先纠正一个前提：现在跑的其实不是"全量扫"

读 `approval_sync.py::sync_part()` 后的事实：

| 项 | 现状 |
|---|---|
| 日常两次（08:40 / 13:59） | `full=False` → **45 天窗口增量**，不是全量 |
| 真正的全量 | 只有手工 `--full`，从 `full_since=2025-06-01` 拉 |
| ID 拉取 | `/topapi/processinstance/listids`，按 29 天切片，老接口**只支持创建时间**，没有修改时间 |
| 详情拉取 | 每个待拉单一次 `/topapi/processinstance/get`，`request_interval_sec=0.15` |
| 关键优化 | `done_cached`：已 COMPLETED 的单**不再请求**；`unfinished_ids`：在途单超出窗口也必拉 |
| 归档库写入 | `archive_part()` 对每一行都 UPDATE 并刷 `updated_at=now`，即使内容没变（这就是全表刷时刻的根因） |

所以 7 分钟不等于"扫了 5095 单详情"，真正耗时是：
**18 个模板的 listids 分页 + 1587 个在途单逐个 get_instance × 0.15s ≈ 4 分钟**，外加导出 18 个 xlsx 与 5095 行 upsert。

这个认知差很重要：优化对象不是"把全量变增量"，而是**把 1587 个在途单的拉取变轻**。

## 1. 业界做法（检索结论）

主流是 hybrid：**增量高频 + 全量周期对账**。共识几条：

- 增量靠 watermark（可靠 `updated_at` / 序列号 / 日志位点）+ **重叠窗口**（lookback，按实测迟到分布取 1~2 天或 15~60 分钟），靠幂等 merge 吸收重复。
- `>` 而不是 `>=` 推进水位线；水位线必须和批次成功**同事务**持久化，崩溃重跑不跳过。
- **增量天然抓不到删除**，必须有周期全量对账兜底。
- full refresh 是 escape hatch，必须一直保持可用；没有全量兜底的增量是"一个 bug 之后的永久漂移"。
- 不要做"扫描全源找变化"的伪增量——那是慢版全量还带 bug。
- 上游不可靠 `updated_at` 时，别硬做 watermark；用 snapshot-diff 或缩短周期。

钉钉的特殊约束：

- 老接口 `listids` 只给 `start_time/end_time`（创建时间），**没有 modified_time**，所以标准 watermark 在这里没有可靠锚点。
- 新版 `/v1.0/workflow/processes/instanceIds/query` 支持 `statuses: ["RUNNING"]` 等状态过滤（**须实测权限与行为**）。
- 宜搭接口 `/v2.0/yida/processes/instanceIds` 有 `modifiedFromTimeGMT`，但那是宜搭表单，不一定覆盖本项目的普通审批模板。

**结论：不追修改时间水位线。** 用「在途单集合 + 重叠窗口 + 全量对账」这套更适合当前数据源。

## 2. 推荐框架：三层脉冲

```
T0  全量对账层   2 次/天   08:40 / 13:59   7 分钟   正确性真源
      ↓ 产出 xlsx + 归档库全量快照
T1  增量脉冲层   每 15 分钟  目标 < 30 秒   只拉在途单，只写归档库
      ↓ 产出 export_rows 的字段变化
T2  变化监听层   每 60 秒   watch/（已落地）    零 API
      ↓ 产出人能读懂的事件
消费层  简报 / 催办 / 面板（本轮不动）
```

### T0 全量对账层（保持现状）

- 频率、脚本、产出**完全不动**。
- 唯一职责升级：作为 T1 的**正确性兜底**——抓删除、历史回补、字段映射变化。
- 保留 `--full` 作为最终 escape hatch。

### T1 增量脉冲层（本框架的新增部分）

三个杠杆，按收益排序：

**杠杆 1：Part8 分流（最大收益）**

实测在途 1587 单里，手机膜 Part8 独占 **1022 单（64%）**。
而你已经明确：Part8 闭环没人做，只需要知道货件运输天数。
→ Part8 不再逐单调钉钉审批详情，改消费平台 `/api/transport`（`watch/http_transport` 源已接好，接口起来就自动生效）。
→ 去掉这 1022 单，在途拉取量从 1587 降到 **565 单**。

**杠杆 2：分片轮询（把 85 秒压到 20 秒）**

565 单 × 0.15s ≈ 85 秒，还不够"短时"。按优先级分片：

| 片 | 环节 | 在途单 | 频率 |
|---|---|---|---|
| A（高频） | Part5 发货 + Part9 检查 | ~466 | 每 15 分钟 |
| B（中频） | Part1/2/3/6/7 | ~99 | 每 30 分钟 |
| C（低频） | Part4 | 1 | 随 T0 |

A 片 466 单 × 0.15s ≈ 70 秒，仍偏慢；若新版 API 的状态过滤可用，可直接拿 RUNNING ID，省掉 45 天窗口分页，再叠加 lookback 去重，预计压到 30~60 秒。**先探针实测，再定频率。**

**杠杆 3：只写归档库，不重写 xlsx**

T1 只 upsert `export_rows`，绝不动 `Part*.xlsx`。
这样 xlsx 的 mtime 仍然只代表"T0 全量产出时刻"，新鲜度守卫的语义不被污染。

### T1 必须守住的五条工程纪律

1. **不拿 `created_at` 当水位线**——创建后改状态的单会漏（业界明确反面教材）。
2. **重叠窗口 15 分钟** + 按 `(product, part, instance_id)` upsert 幂等，吸收时钟偏差和最终一致性。
3. **不追删除**——T1 不处理删除，交给 T0；`watch` 的 `deleted` 事件负责告警。
4. **水位线与成功同事务**——本轮任一模板失败就不推进 `last_run`，下轮重跑，绝不跳过。
5. **全程只读钉钉、只写自己的归档库**；不碰 xlsx、不碰核心脚本。

### T2 变化监听层（已落地，无需改造）

`watch/` 每 60 秒扫归档库行级指纹 + xlsx mtime + 平台运输，产出事件流。
它是 T1 的天然消费者：T1 写库 → T2 立刻看到字段变化。零 API 调用。

## 3. 一个漂亮的效果：不用改简报就能防催旧数据

T1 只写库不写 xlsx，会导致归档库 `MAX(finished_at)` 比 xlsx mtime 新。
而现有的 `rules/freshness.py::assess_freshness()` 恰好把这种情况判为 **BLOCKED**：

> "快照已被超越：数据截至 14:07，但后台已同步到 15:30 —— 本次禁止催办"

也就是说：**T1 一产生新数据，简报自动停止按旧快照催办**，不需要改 `daily_brief.py` 一行代码。
这是第一层新鲜度守卫的复用价值。

代价：T0 跑完后 xlsx mtime 追上库，BLOCKED 解除，简报恢复。中间这段时间宁可不催，也不催错——这正是你要的。

## 4.1 P1 实测结果（2026-11-16，真实钉钉接口，全程只读）

探针 `scripts/probe_incremental.py`，改的是独立新文件，未碰任何同步代码/业务库。
权威报告 `scripts/_p1_probe_final.json`（干净轮，无 QPS 命中）。

### 结论一：新版 `statuses` 过滤可用 ✅

同一时间窗（45 天）三次查询，翻页到底后：
- `RUNNING ∩ COMPLETED = 0`（集合互斥）
- `RUNNING ⊆ NO_FILTER`、`COMPLETED ⊆ NO_FILTER`（都是子集）
- 反查 RUNNING 集合 5 个 ID 的真实状态：**5/5 全是 RUNNING**

→ 可以直接用 `statuses:["RUNNING"]` 拿在途 ID，不必拉全量再本地过滤。

**两个坑（已写进探针）**：
1. `maxResults` 合法值只有 **1~20**，≥50 报 `InvalidmaxResults`。
2. 验证过滤时若 `max_pages` 太小（如 2 页），三种过滤都会被截断在同一页数、前 N 个 ID 看起来相同 → 误判"过滤无效"。**必须用集合互斥 + 反查状态判据，不能比 id_count。**

### 结论二：API 的 45 天窗覆盖不到大部分在途单 ⚠️

全 18 模板对账（45 天窗 RUNNING vs 缓存全量在途）：

| 口径 | 数量 |
|---|---|
| 新版 API 45 天窗 RUNNING 合计 | **362 单** |
| 缓存全量在途合计 | **1462 单** |
| 缺口 | **1100 单** |

缺口集中在 **Part8（缓存 1022 vs API 138）和 Part9（213 vs 24）**——这些在途单创建时间远超 45 天，时间窗够不着。
→ **T1 必须"时间窗 RUNNING ∪ 缓存在途集合"取并集**，正因为如此，框架第 1 节 `unfinished_ids` 兜底不是可选项而是必需。

### 结论三：耗时与限流 ✅（可承受）

- 详情拉取单实例均值 **0.138 秒**；Part5 在途 169 单外推 **≈23 秒**。
- 全 18 模板扫一遍 RUNNING ID（只取 ID 不取详情）**16.9 秒**。
- **接口级 QPS 上限 100/秒**（`workflow_1.0#ListProcessInstanceIds`），按秒窗口，撞到只封 ~1 秒；错误里明确"建议错开整点"。探针用 `interval=0.6s` 干净跑完 43 次调用零命中。
- 从 2 次/天 → 96 次/天，只要**单次脉冲压在几十次调用 + 避开整点 + 模板间加 0.3~0.6s 间隔**，QPS 不是瓶颈。

### P2 建议参数（据实测修正）

1. T1 增量集 = `新版 query(statuses=RUNNING, 45天窗)` ∪ `缓存里 status!=COMPLETED 的集合`，按 `(product, part, instance_id)` 去重。
2. 只拉增量集里**本地状态与远端不同**的单详情（靠缓存跳过已完成），调用数从 1462 降到数百级。
3. Part8 的 1022 在途单仍按既定方案分流到平台 `/api/transport`，不进钉钉详情拉取。
4. 模板间 `sleep 0.3~0.6s`，整点前后 1 分钟不跑，QPS 兜底加 1.2s 退避重试。
5. `maxResults=20` 分页；水位线/成功标记与批次同事务。

## 5. 风险与红线

- **上游配额**（P1 已答）：接口级 QPS 上限 100/秒（秒级窗口，撞到只封 ~1 秒，建议错开整点）。日配额未见明确数字，但单次脉冲压在数十次调用 + 模板间隔 0.3~0.6s 下，96 次/天风险可控；P3 仍需观察 3 天实际调用量。
- **Part8 分流覆盖度**：平台 `/api/transport` 必须有足够数据，否则 Part8 会失去监听。切之前先比对两边数量。
- **增量漂移**：靠 T0 每天两次全量对账兜底；若连续多日 T0 失败，必须告警而不是静默。
- **不要 hand-roll streaming**：分钟级用 cron + 幂等就够，别引入 Kafka/CDC 那套固定成本。
- **核心不动**：本轮所有新增都是独立文件；P4 之前不碰 `daily_brief.py` / `plugins/workmain.py` / 数据后台。
