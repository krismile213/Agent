# LLM Wiki POC 对比报告

> 日期：2026-11-17
> 背景：Karpathy 2026-04 提出 LLM Wiki 模式，业界有"替代 RAG"的说法。
> 本 POC 用项目现有权威源做小规模验证，回答两个问题：①效果差别大吗？②能不能替代现有 RAG？

## 一、结论先行

**不能替代，但值得作为 L1 稳定底座旁路引入。** 同一评测集 6 条，两者互有胜负：

| 架构 | top1 命中 | 来源召回 | 事实可见 | 依赖 |
|---|---|---|---|---|
| RAG（BM25+向量+RRF+语义繁化） | 4/6 | 6/6 | 6/6 | 本地 embedding 模型 + 4546 块索引 |
| Wiki（编译期固化 + 整页返回） | 5/6 | 6/6 | 5/6 | 零 embedding / 零模型 / 66 概念页 |

- Wiki 的 top1 更高（5 vs 4），因为"编译期预综合"把口语锚点固化进页面，查询时字面匹配即可，不依赖小模型的语义泛化能力。
- RAG 的事实可见更稳（6 vs 6 vs Wiki 5），因为它保留了所有原文的细粒度 chunk，Wiki 的按标题切页在个别页上把事实"埋"进了长正文。
- **关键差异在成本结构**：Wiki 把计算从"每次查询"移到"一次编译"，查询零推理成本、完全确定性、可审计；RAG 每次查询都要跑向量相似度。

## 二、Wiki 模式原理（Karpathy 三操作）

1. **ingest（编译）**：把精选权威源一次性"读透"，编译成结构化概念页——每页带固化别名、事实表、来源。计算集中在导入期。
2. **query（查询）**：先读索引（整库地图），再按别名/标题/事实加权匹配，整页返回。知识已预综合，无需每次重新检索推理。
3. **lint（体检）**：周期性扫描源漂移、口径数字冲突、孤儿页——相当于给知识库跑 CI。

**适用边界**：约 150~200 页 / 5~10 万 token 以内、强权威、稳定、有 owner 维护。超过规模索引撑爆上下文；数据变得快则重编译成瓶颈。

## 三、对本项目的判断（为什么不替代而是分层）

| 适合编译成 Wiki 底座 | 必须留在 RAG / 直读 |
|---|---|
| 口径内核 rules/targets（Part1=13 等真源） | xlsx 订单流 / 到货数据（T0/T1/T2 每 15min 变） |
| SOP / 使用说明 / 规则快照（少·精·权威·稳定） | 开放问答 / 海量资产文件（编译进 wiki 必然 stale） |

- 项目其实已做了 wiki 化的一半：把口径抽成单一真源 = 编译期沉淀。**缺的是 lint 层**（本次 POC 补上）。
- 建议架构：**Wiki 当 L1 稳定底座**（口径/SOP，一致性高、可追溯、查询零成本），**RAG 当 L2 动态检索**（订单流/开放查询，新鲜、覆盖广），中间一个路由决定问题走哪条。

## 四、POC 实现（旁路，不动核心）

- 编译器：`plugins/knowledge_wiki.py`（纯标准库，零 LLM 依赖，不 import rag）
  - 5 篇权威源 → 66 概念页（409K）；编译幂等（内容 hash 不含时间戳）；只读源
  - **防造假**：固化别名只含概念词/口语说法，不含任何答案数字（60/15/13）
  - 产物在 `wiki/`（gitignore，可重建）
- 查询：`query_wiki()` 加权字面匹配（别名×5 / 标题×3 / 事实×2 / 正文×1）
- 体检：`lint_wiki()` 源 hash 漂移 / 口径数字冲突 / 孤儿页
- 测试：`scripts/test_knowledge_wiki.py` 15/15
- 对比：`scripts/eval_wiki_vs_rag.py`（复用 test_rag.py 的 6 条查询）

### 调参记录（POC 暴露的真实问题，已修）

1. 初版 top1 把"红线"查询路由到 Part3（因标题含"全流程关键闸门"被灌入"红线"别名）→ 拆分强弱锚点：红线/总周期只给真正讲总周期的页。
2. 初版 lint 误报 12 条"数字冲突"（把不同 Part 的时效聚到同一 key）→ 改为按口径主题归一，容许换算值。修后 lint OK。

## 五、边界与后续

- 本 POC 是**检索级**评测（无 LLM 答题），只验证召回/事实可见，不验证最终回答质量。
- Wiki 索引目前是字面匹配，未接入 LLM 做真正的"预综合写页"——这是 Karpathy 原版的核心，本 POC 用规则固化别名近似，换取确定性与零成本。
- 若要生产化，下一步是：①加 lint 到简报/监听链路做口径漂移告警；②Wiki-first / RAG-fallback 路由；③评估 LLM 编译写页的收益是否覆盖成本。
