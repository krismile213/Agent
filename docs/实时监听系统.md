# 联合实时监听系统（POC）

> 状态：**第一版已落地并实测通过**（2026-11-16）。旁挂只读，未改动 `daily_brief.py`、
> `plugins/workmain.py`、数据后台任何代码。
> 代码：`watch/`；测试：`scripts/test_watch_core.py`（38 项，已挂 fast 回归）。

## 1. 解决什么问题

定时简报是「快照制」：14:20 拿 14:07 的数据催办，17:00 对方办完了，
Agent 不知道，还在按旧状态催 —— 催了已完成的事。

根因不是话术，是**没有变化信号**。本系统持续监听各后台的数据变化，
把「哪张单、哪个字段、几点、从什么变成什么」记成事件流，供后续决定
「还要不要催 / 催什么」。

## 2. 边界（硬约束）

| 约束 | 做法 |
|---|---|
| 不动核心 | 不 import `daily_brief` / `plugins.workmain` / 数据后台 app；只复用 `rules.freshness` 这类纯函数 |
| 只读源 | 归档库 `mode=ro` 打开；Part 文件只 `stat` 不读内容 |
| 物理隔离 | 事件只写 `watch/watch.db`，与源库分离；`--reset` 也只清自己的库 |
| 可降级 | 任一源坏掉/离线 → 该源 `skipped` 并记录原因，整轮不崩 |
| 可测试 | 指纹/diff 是纯函数；引擎接受注入 sources 与时钟；全部单测用临时库 |

## 3. 数据源

| 源 | 信号 | 粒度 | 实测 |
|---|---|---|---|
| `sqlite_rows` | `dingtalk/export_archive.db::export_rows` 的 `row_json` 指纹 | 单条审批单 | 5095 行，0.26s |
| `export_runs` | 同库 `export_runs` 按 `started_at` 聚合 | 一轮同步 | 40 轮 |
| `part_files` | `data/<品类>/<品类>/Part*.xlsx` 的 mtime/size | 品类 × 环节 | 18 份 |
| `http_transport` | `GET :8000/api/transport` 逐票 | 单票货件 | :8000 未起时 skipped |

### 为什么不用 `export_rows.updated_at`

每轮同步会把全表 `updated_at` 刷成同一时刻（实测 5095 行全是
`2026-11-16T14:06:37`）。它测的是「同步动作」，不是「业务变更」。
用它判变化 = 每轮 5095 条假事件。

本系统只对 `row_json` 里的业务字段做指纹。**实测反证**：把全表
`updated_at` 改掉、业务字段不动 → 0 事件。

### 「更新时间」为什么保留

`row_json` 里的「更新时间」有 4575 个不同取值，是钉钉单据的业务时间，
必须参与指纹。被剔除的只有 `updated_at` 这类技术列。

## 4. 事件模型

```
events(id, detected_at, source, entity, kind, part, product, changes_json, payload_json)
kind ∈ created | updated | deleted | sync_finished | baseline
changes = [{field, old, new}]   # 只含真正变化的字段，值截断 200 字
```

`entity` 是稳定主键：

- 审批单：`品类|instance_id`
- 同步批次：`started_at`
- 快照文件：`品类|PartN_环节名`
- 货件：`货件号`

`state(source,key,hash,data_json)` 存上一轮快照，用于 diff。
`runs` 存每轮审计（扫描数/事件数/跳过源/异常）。

## 5. 用法

```bash
# 扫一轮（首轮自动建基线，不产事件）
python -m watch --once

# 常驻轮询（60s 一轮）
python -m watch --loop --interval 60

# 看事件 / 统计
python -m watch --tail 20
python -m watch --stats

# 只启用某几个源
python -m watch --once --source sqlite_rows --source export_runs

# 首轮把全量标成 baseline 事件（默认不产，避免 5095 条噪音）
python -m watch --once --emit-baseline

# 清空监听库（不动源）
python -m watch --reset --yes
```

配置来源：`config.json` 的 `workmain_root` / `platform_root`；
可用 `--root --db --platform` 或环境变量 `AGENT_WATCH_ROOT / AGENT_WATCH_DB /
AGENT_WATCH_PLATFORM / AGENT_WATCH_SOURCES / AGENT_WATCH_INTERVAL` 覆盖。

## 6. 实测（2026-11-16）

真实全源基线：

```
scanned=5153  baseline=3  skip=1   # 5095 单 + 40 轮同步 + 18 份快照
第二轮 scanned=5153  events=0      # 幂等
```

真实库副本变更演练（9MB 副本，非源库）：

| 动作 | 结果 | 耗时 |
|---|---|---|
| 基线 | 5135 行 | 0.26s |
| 改 1 条「审批状态」 | **1 条 updated**，`审批中 → 已完成` | 0.35s |
| 再扫一次 | 0 事件 | 0.20s |
| 全表刷 `updated_at` | **0 事件**（核心防线） | — |

## 7. 已知边界 / 下一步

**还没做（等点头）：**

1. **B 档：上架日期回写** —— Part8 到货后自动关单需要「手机上架日期」，
   目前该列全空，闭环缺最后一环。
2. **推送与展示** —— 事件库已可查，但还没有 Web 页面/钉钉推送消费它。
   建议先只做「每小时汇总一条」，别做成逐条刷屏。
3. **第二层轻量同步** —— 现在监听的是「后台已经拉下来的数据」；
   要真正做到分钟级，需要让钉钉同步从 2 次/天提到 15min 一次
   （这一步会压到上游审批接口，得先确认限流）。
4. **平台运输口径** —— `:8000` 在线时 `http_transport` 会自动生效；
   当前离线，源状态记为 skipped，不影响其他源。

**刻意没做：**

- 没把监听挂进 `server.py` / `daily_brief.py`（先证明内核可靠，再谈接入）。
- 没做自动催办（监听只提供事实，催不催是业务决定）。

## 8. 测试

`scripts/test_watch_core.py` 覆盖 38 项：

- 指纹：键序/空白/`updated_at` 不影响结果；业务字段变则变
- diff：updated/created/deleted 三态；字段级 only；超长截断
- 端到端：基线不产事件 → 变更/新增/删除各归位 → 幂等 → 源库 mtime 不变
- 同步批次：一轮同步聚合为一条 `sync_finished`
- 文件源：品类隔离（手机膜/手机壳同名 Part 不串号）+ mtime 变化
- 降级：坏库/坏目录/坏 URL 全部 skipped 不崩
- `--emit-baseline`：基线事件 kind 独立

运行：`python scripts/test_watch_core.py` 或 `python scripts/run_all.py --tier fast`。
