## 一、背景与目标流程

### 1.1 现状（旧流程）

Part6（寄送拍摄/素材加工）的**建单前提**是 Part3（本地仓到货检查）通过：

```
产品/素材轨:  Part1提案 → Part2签样采购 ──✗ 被闸──→ Part6寄送拍摄 → 素材加工 → Part4/7上架+广告
                                    │
后勤/发货轨:  Part3本地仓到货 ──────✓ 放行──→ Part5发货        （Part8渠道仓到货、Part9审批独立走）
```

2026-11-05 已按"Part3→Part6 硬依赖"落地了三处代码（详见 §3.2 的「旧逻辑」），
本方案将该依赖**降级为间接约束**。

### 1.2 目标（新流程）

```
产品/素材轨:  Part1提案 → Part2签样采购 → Part6寄送拍摄 → 素材加工 → Part4/7上架+广告
                                              ↑
后勤/发货轨:  Part3本地仓到货 → Part5发货      （间接约束：影响节奏，不阻塞建单）
```

**改动一句话**：Part6 的前置从 Part3 改挂 Part2；Part3 之后只连后勤发货线（Part5）。

### 1.3 「间接约束」的两种理解（⚠️ 待业务确认，决定代码写法）

| 理解 | 含义 | 代码落点 |
|---|---|---|
| A. 节奏联动 | Part3 慢会拖整体在研周期，但不影响 Part6 建单与寄送 | 只改文案与复盘口径，不加判定逻辑 |
| B. 实物依赖 | 某些素材（场景图/细节图）仍需正式到货产品，签样只能拍基础素材 | Part6 模板加可选提醒字段 + 数据后台「间接影响」标注列 |

**建议**：先按 A 落地（改动最小），B 若业务确认再追加。

## 二、钉钉流程修改方案（审批后台操作）

> 操作人：钉钉后台管理员。改模板前先备份当前模板截图/字段清单（check_field_parity.py 的 diff 依据）。

| # | 改什么 | 具体操作 |
|---|---|---|
| 1 | **Part6 发起前置** | 审批流「寄送拍摄团队」的发起条件/前置节点：从「Part3 本地仓到货检查通过」改为「Part2 全套样品测试完成（签样）」 |
| 2 | **Part5 发起前置** | 审批流「发货」确认前置 = 「Part3 本地仓到货检查通过」（如果原本没有显式前置，补上，让系统约束与流程图一致） |
| 3 | **Part6 模板字段** | 若存在「关联 Part3 单号」字段 → 改为「关联 Part2 单号」；系统业务时间列（寄送拍摄团队日期/拍摄团队素材交付日期）**保持不变** |

**存量在途单的处理**：
- 切换时点已完成的 Part6 单（旧口径建的）：保留不动，复盘按旧口径解释。
- 切换时点 Part6 未建、签样已完成的 SKU（如 G599-G607 这批卡在 Part3 的）：
  **切换后按新规则立即可建 Part6**——会出现"寄送早于本地仓到货"的数据形态，
  这正是业务真实节奏（实测历史中位并行 4 天），复盘口径要按新流程解释（见 §3.4）。

## 三、事中汇报代码修改预案（数据后台系统，main 分支）

### 3.1 段级规则 `backend/app/seg_rules.py`

**基本不用动**——段定义起点本来就是签样：

```python
("产品", "签样→寄送", "签样", "寄送", 5, "李杰华", "★起点改签样", False),
```

需检查/微调：

| 位置 | 改动 | 说明 |
|---|---|---|
| `NODES["寄送"]` | 不变 | 仍锚 Part6「寄送拍摄团队日期」 |
| `SEGS` 后勤段「采购→本地仓到货(8天)」 | 不变 | Part3 时效口径不变 |
| `L4 = ("后勤","采购→发货末批","采购",22,...)` | **可选改**：起点「采购」→「本地仓到货」 | 新流程 Part3→Part5 连线后，发货目标锚本地仓到货更贴业务；⚠️ 目标 22 天需重校准，涉及 rule_config 同步，**建议单独立项** |
| `PRODUCT_END_NODE = "素材加工"` | 不变 | 部门边界不受影响 |

### 3.2 流程依赖判定 `backend/app/inflight_service.py` —— 核心改动

**旧逻辑**（`_dep_rules()`，约 330-363 行，2026-11-05 落地）：

```python
p6_missing = not (parts_docs.get("Part6") or [])
p3_running = any(d.get("status") == "审批中" for d in (parts_docs.get("Part3") or []))
# ① Part6 未建单 → 「签样→寄送」摘出停留/超期/预警（因为建不出来）
# ② Part3 审批中 → 「采购→本地仓到货」按未完成重判（seg_state force_open）
# ③ 素材通用 → Part6 三段整段跳过
```

**新逻辑**（流程改后替换 ①，②③ 保留）：

```python
def _dep_rules(parts_docs, mat_generic):
    """2026-XX 流程修改后：Part6 挂 Part2（间接约束版）。
      ① Part6 未建单：
         - 若 Part2 签样已完成 → 产品部该建单没建，「签样→寄送」照常判定
           （真实卡点 = 产品部建单/寄送动作，要催）；
         - 若 Part2 签样未完成 → 「签样→寄送」摘除（还没轮到），原因文案改为
           "签样未完成，寄送未开始"。
      ② seg_state force_open 保留：Part3 审批中时「采购→本地仓到货」按未完成
         重判 —— 该逻辑只关系 Part3 自身时效，与 Part6 无关，不受本次修改影响。
      ③ 素材通用跳段保留，但说明文案改：「签样完成后直进上架 Listing+广告」。
    """
```

同文件联动改动：

| 位置 | 改动 |
|---|---|
| `compute_inflight` 里调用 `_dep_rules` 后构造 `part6Blocked` 的逻辑 | 语义从「Part6 被 Part3 阻塞」改为「Part6 未建单 + 签样未完成」；或直接改名为 `p6Pending`，**前端有引用要同步**（搜 `part6Blocked`） |
| `genericMaterial/genericBasis` item 字段 | 不变 |
| 摘除原因文案（`dep_muted` 的 value） | 全部按 1.2 新因果链重写，**别让前端图例/快照里残留"卡在本地仓到货检查"字样** |

### 3.3 素材通用 `backend/app/generic_material.py`

判据本身不变（拍摄=否 或 有素材参考 → 通用）。仅改 `judge()` 返回的
`basis` 文案与跳段说明：「本地仓到货后直进上架」→「签样完成后直进上架」。

⚠️ **连带业务问题（待确认）**：素材通用 SKU 的上架前提，旧口径是"本地仓到货"，
新流程下若 Part6 也跳过，上架前提变成"签样完成"——与 Part4 首次上架（锚采购）
的既有口径是否冲突，需要运营确认。

### 3.4 复盘/甘特口径

- 在研甘特（dates_mode）按 SEGS 渲染，段名不变 → 自动适配。
- **新数据形态的解释**：新流程下会出现大量「寄送日期 < 本地仓到货日期」的 SKU
  （正常并行，不是反向）。`route_check_sys` / 复盘报告里若有「⚠反向」校验，
  需给 Part6 相关段加豁免说明（搜 `反向`）。
- 存量 vs 增量：切换日期前的 SKU 按旧口径复盘，之后的按新口径——复盘报告
  加一行口径分界说明即可，不建议写双轨判定代码。

### 3.5 测试预案（tests/test_inflight.py）

2026-11-05 加的 6 个断言（基线 622 passed/1 skipped）中：

| 断言 | 处置 |

| Part6 未建单的 SKU 不得催寄送（p6_missing → 摘除） | **改写**：仅在「签样也未完成」时摘除；签样已完成且 Part6 未建 → 必须出现在停留/预警里 |

## 四、钉钉自动化导出修改预案（work-main/dingtalk）

> 同步链路：`\DingTalkApprovalSync` 计划任务（08:40/13:59）→ `run_scheduled.py`
> → `approval_sync.py` 拉单 → `Part*_<时间戳>.xlsx` → 数据后台/Agent 消费。

| 环节 | 是否要改 | 说明 |
|---|---|---|
| `approval_sync.py` 拉单 | **不用改** | 按模板清单拉全部审批单，模板前置变了不影响拉取 |
| `check_field_parity.py` | **不用改，但要盯** | 流程修改后第 1~2 轮同步若报字段差异（Part6 新增/删除字段），属**预期内**——对照 §二-3 的模板字段改动人工确认后放行 |
| Part6 导出列 | 可能变 | 若模板加「关联 Part2 单号」，Part6_*.xlsx 多一列；下游（数据后台 review 导入、Agent 取数）按列名取值，多列无感 |
| `run_scheduled.py` 第三步 | 不动 | check_field_parity 继续挂着，起"改流程必先报出来"的哨兵作用 |
| 建单时间点前移 | 无代码影响 | Part6 单据 create_time 会明显提前（签样即建），同步与下游都按实际时间消费 |

**操作顺序提醒**：钉钉后台改模板 → 手动触发一轮 `run_sync.bat` → 看
`check_field_parity` 输出 → 确认差异与预期一致 → 再让定时任务自然跑。
