# 钉钉群通知原理

> 一句话：**不是「让模型写日报、然后发出去」，而是「代码取数 → 模型只写三节 → 代码渲染三节 → 代码质检 → 分片推送」。**
> 模型的职责被压缩到「读懂问题 + 组织语言」两件事，凡是能算的、能判的、能格式化的一律交给代码。

本文写的是 **Agent 侧的钉钉线**（审批同步数据 → 群里两条通知）。
数据后台的**平台事中日报线**是另一套口径，见 `docs/事中日报对接说明.md`，两套结论不可互相引用。

---

## 0. 涉及文件

| 文件 | 职责 |
|---|---|
| `run_brief.bat` | 计划任务入口。探测能 `import pandas, requests` 的解释器，然后转发参数给 `daily_brief.py --push` |
| `run_brief_pm.bat` | 午后专用包装，只做一件事：`call run_brief.bat --pm` |
| `daily_brief.py` | 主流程：装配注册表 → 预取 → 调模型 → 渲染 ③④⑤ → 质检修复 → 合并落盘 → 推送 |
| `dingtalk_push.py` | 推送层：加签、Markdown 换行修正、分片、发送 |
| `plugins/workmain.py` | 业务工具（`sync_status` / `scan_sync_data` / `pipeline_alerts`）与全部口径常量 |
| `briefs/<YYYY-MM>/<日期>.md` | 落盘产物，一天一份 |
| `briefs/task.log` | 计划任务日志（编码混排，读的时候用 `errors="replace"`） |

## 1. 触发与运行

### 1.1 两个计划任务

| 任务名 | 触发 | 动作 |
|---|---|---|
| `AgentDailyBrief` | 每天 09:00 | `run_brief.bat --am` |
| `AgentDailyBriefPM` | 每天 14:20 | `run_brief.bat --pm` |

午后排在 14:20 而不是 14:10，是为了**避开平台侧写日报的时段**。同一时段抢同一个 Excel，会撞 `PermissionError`，那次是 `DataAdmin-AutoPipeline` 失败的直接原因。

### 1.2 解释器探测（`run_brief.bat`）

历史坑：旧版写死 `C:\Python314\python.exe`，而那个解释器**一个第三方包都没有**，跑起来第一行就 `ModuleNotFoundError: pandas`，但任务面板还显示「成功」。

现在的做法是**探测**，按优先级取第一个真能用的：

```
1) C:\Users\dell\AppData\Local\Python\bin\python.exe
2) C:\Users\dell\.workbuddy-ai\binaries\python\envs\default\Scripts\python.exe
```

判定条件是 `import pandas, requests` 同时成功。只测 pandas 不够——`agentcore` 和 `dingtalk_push` 在 import 期就要 `requests`，只测一半会在下一行再死一次。

### 1.3 晨检 / 午后的判定

`resolve_run_slot(pm_flag, am_flag, now)` 的优先级：

1. 显式 `--pm` → 午后
2. 显式 `--am` → 晨检
3. 都没给 → 退回挂钟：`hour >= 12` 判午后

`--am` / `--pm` 存在的原因，是挂钟推断会在两种情况下**静默判错段**：

- a) 午后任务失败、延到次日上午补跑 → 被判成晨检，午后内容写进晨检段，把当天真正的快照顶掉；
- b) 晨检拖过 12:00 才跑完 → 被判成午后，覆盖正常的午后段。

> ✅ **2026-11-01 已修**：两个计划任务现在都显式带参数（`AgentDailyBrief --am`、`AgentDailyBriefPM --pm`），不再依赖挂钟。
> 采行方案是把参数直接挂在 `run_brief.bat` 上，而不是让任务指向 `run_brief_pm.bat`——这样在任务管理器里一眼就能看出这一段到底是晨检还是午后，少一层 bat 嵌套。`run_brief_pm.bat` 保留作**手动入口**（`call run_brief_pm.bat` 等价于 `run_brief.bat --pm`）。
> 改之前的任务 XML 备份在 `D:\data\sched_backup\`。
> 效果：此后即使午后任务延到次日上午补跑，也会被 `--pm` 正确判成午后段，不会再顶掉当天的晨检快照。

## 2. 装配：只读注册表

```python
build_readonly_registry(cfg)   # daily_brief.py
```

把 `level != "read"` 的工具**全部摘掉**后再交给模型。写文件、跑脚本、外发消息这些工具在无人值守场景里根本不存在。

这是整条链路敢挂在计划任务上的前提：**不是靠提示词约束模型别乱来，而是它手上没有那个工具。**

当前实测（2026-11-01）：注册表共 **34** 个工具 = 只读 27 + 写 6 + 外发 1。被摘掉的是这 7 个：

```
write_file   undo_write   run_python   save_memory
dingtalk_send   kb_build   run_route_check
```

其中 `dingtalk_send` 值得单独说明：它**是**注册过的工具（external 级），交互模式下能用，但会先弹一屏「外发草稿」让人确认——标题、字数、正文前 800 字，且不支持「本会话总允许」。发出后不可撤回，所以这个确认不能省。

到了无人值守的晨检里，它连同其他 6 个一起被摘掉。**结论：聊天时不会自己往群里发消息，「发不发」由代码决定，不由模型决定。**

## 3. 取数：预取，而不是让模型自选

```python
PREFETCH_TOOLS = ("sync_status", "scan_sync_data", "pipeline_alerts")
prefetch_tool_data(registry)   # 代码先跑一遍
prefetch_prompt(data)          # 结果拼进提示词末尾
```

**为什么要这样做**：2026-10-23 实测，提示词里写了「③④⑤ 不用你写条目」，模型直接 **0 次工具调用**，凭空气编出三条「今日动态」。否定式指令压不过「必须取数」这条正向要求，靠提示词不可靠。

改成预取之后，模型的输入里已经带着三份实时数据，它没有「不查」这个选项。

失败降级：单个工具取数失败不中断，写入 `[取数失败: ...]` 后继续，最终由质检环节判定。

## 4. 分工：六节谁写

晨检是完整快照，固定六节。**其中三节由模型写，三节由代码渲染。**

| 节 | 标题 | 产出方 | 依据 |
|---|---|---|---|
| ① | 同步状态与数据截至 | 模型 | `sync_status` 的 `[结论]` 行 + 数据截至时间 |
| ② | 今日动态 | 模型 | `scan_sync_data` 的「今日有动态」 |
| ③ | 新增SKU与签样追踪 | **代码** | `pipeline_alerts` 第 1 组，逐字渲染 |
| ④ | 临期预警 | **代码** | `pipeline_alerts` 第 2 组，逐字渲染 |
| ⑤ | 已超期与环节停滞TOP | **代码** | `pipeline_alerts` 第 3、4 组，逐字渲染 |
| ⑥ | 行动建议 | 模型 | 基于上面真实出现的 SKU，≤3 条 |

节标题由 `SECTION_TITLES` 常量固定，模型写的标题、编号、列表符号都会被 `normalize_brief_md()` 重排成统一形状。

## 5. 各节判据

### ① 同步状态与数据截至

- **唯一判定来源是 `sync_status` 输出里的 `[结论]` 行**（✅ / ❌ / ⏳）。
- **数据截至日没有推进 ≠ 同步故障**。周末没有审批，数据自然会停在前一场，这是正常状态。
- 禁止推断日志里没有的故障原因。

> 这一条最容易误读：群里看到「同步正常 · 数据截至 10-22 17:39（未推进）」会觉得自相矛盾，其实是正确结论——判的是同步任务，不是审批活跃度。

### ② 今日动态

- `scan_sync_data` 的「今日有动态」是**唯一来源**。
- 有明细就逐条给：`SKU + 型号 + Part + 最新节点 + 当前负责人`。
- 写「0 单」就输出「今日无新增动态」，不解释、不铺垫。
- `pipeline_alerts` 的「Part9 新单待办」只能作补充，工具只给 4 个字段，不许扩写。

### ③ 新增SKU与签样追踪

- 窗口是 **滚动 40 天**（`NEW_SKU_WINDOW_DAYS = 40`），**不是自然月**。跨月时会与上月重叠，这是有意为之：30 天太窄，窗口边缘刚签样就掉出去了。
- 签样目标按品类分别配置：手机膜 12 天（锚 Part1 取数）、手机壳 87 天（锚创建时间）。两者锚点不同，不能互换。
- 条目内容由 `render_data_sections()` 从工具输出逐字填充，模型不参与。

### ④ 临期预警

- 按剩余天数升序排列。
- 必须带一行计数 `临期 N 个`——午后的数字校正靠它对齐；没有计数就只能写「晨检未记录总数」，是没有信息量的噪音。
- **0 个也必须出节**。2026-10-29 实测：旧写法 `if items` 在「临期 0 个」时跳过 ④，简报从六节变成五节，读者以为是漏报。「0 个」本身是有效结论，要靠正文说出来，不能靠标题消失来表达。

### ⑤ 已超期与环节停滞TOP

两组内容，共用一份工具输出：

- **已超期**：按超期天数排序，带 `已超期 N 个` 计数。
- **历史遗留截断**：`STALE_CAP_DAYS = 120`。超过 120 天的归入「历史遗留 N 单，不列入 TOP」，多为悬挂老单，混进 TOP 会把真正需要催的挤下去。
- **环节停滞**：口径是**段级近似**——「距最后更新天数 vs 该环节目标天数」。同一个 SKU 在多个环节都停滞时会在列表里重复出现，这是口径特性，不是 bug。

### ⑥ 行动建议

- ≤3 条，必须指向上面真实出现过的 SKU：谁、卡在哪、要做什么、什么时候前完成。
- 引用工具输出里不存在的 SKU，会被 `drop_ghost_skus()` 删除并计数。
- 为什么这么严：2026-10-23 出现过「提醒某人处理 G533」这种指向**虚构的人 + 虚构的状态**的建议，是顺着编造的 ② 一路编下来的。

## 6. 质检与修复

### 6.1 `brief_health()` 检查项

| 检查 | 说明 |
|---|---|
| 缺节 | 晨检要求六节齐全（午后的增量段不要求） |
| 提示词回声 | 正文里出现提示词原句（如「以下是今日晨检报告」） |
| 连续重复行 | **只查 ①②⑥**；③④⑤ 是代码渲染的数据段，重复属数据特性（见 6.4） |
| 括号未闭合 | **只查 ①②⑥**，判据同上 |
| ⑤ 无条目 / 缺环节停滞组 | 少一组等于少报一类风险 |
| 幽灵 SKU | ① ② ⑥ 里出现工具输出中没有的 SKU |
| 占位符 | `[系统自动填充]` / `（由系统填充）` 这类行在 `normalize` 阶段直接丢弃 |

最后一条是核心：`tool_out` 为空时（本次没取到数）不做幽灵 SKU 判定，避免误杀。

### 6.2 修复链

```
brief_health 报问题
  → repair_brief_answer()        带问题清单让模型重写一次
  → replace_dynamic_section()    ② 仍编造就按工具输出确定性重建
  → drop_ghost_skus()            删除 ⑥ 里引用不存在 SKU 的建议
  → 仍有问题则只告警，按清理后的正文落盘
```

顺序不能颠倒：先让模型自己改，改不掉才由代码强制覆盖。代码覆盖是兜底，不是主路径。

### 6.3 收尾重渲染（2026-11-04 补）

**修复链会让模型重写整篇，而 ③④⑤ 的替换在最前面只做过一次** —— 模型重写时会把这三节写成 `[系统自动填充]`，占位符直接落盘推群。11-02 / 11-03 / 11-04 连续三天就是这样。

所以 `finish()` 在**晨检出口最后**再加一次 `replace_data_sections()`：数据段是代码真源，只要取到就无条件覆盖回去，幂等、无副作用；取不到则保持现状不动。

日志里对应这一行：

```
[午后更新] ③④⑤ 收尾重渲染: ③/④/⑤
```

### 6.4 为什么体检不再扫 ③④⑤

段级口径下，同一 SKU 会在多个环节各出现一行。当它在同一环节重复出现时，工具输出会有两行**一字不差**，渲染出去就像复读。旧体检对这种重复计数，判成「连续重复行 3 处」→ 触发重修 → 模型写占位符 → 落盘。**一个数据特性，摧毁了整份日报。**

两道处置：

1. `_pa_items()` 渲染前保序去重，完全相同的行只留第一条（顺序本身有含义，不排序）；
2. `brief_health()` 的复读 / 括号未闭合只查 ①②⑥ —— 那才是模型真正会写坏的地方。

### 6.5 空壳防线

```python
BRIEF_MIN_CHARS = 100      # 晨检正文下限
PM_MIN_CHARS = 30          # 午后增量下限
```

正文不足下限时：**照常落盘、但不推送、退出码 1**。

理由：数据已经取到了（工具轮成功），只是生成被限流掐空。这种时候推一条半截消息占群，不如不推；退出码非 0 能让任务面板看见，人工或下次运行补上。

## 7. 午后：同一份文档的增量段

午后的定位不是「再出一份完整报告」，而是**同一份日报的第二段**。

### 7.1 落盘形态

一天只有一份 `briefs/<YYYY-MM>/<日期>.md`：

```markdown
# 日报 2026-11-01

> 更新记录: 晨检 09:00(完整快照) · 午后更新 14:20 · PM(只列相对晨检的变化)

## 晨检 09:00
…六节完整快照…

---

## 午后更新 14:20 · PM
…只写相对变化…
```

`compose_daily()` 的行为：

- 只有晨检 → 只写晨检段
- 晨检后再跑午后 → **晨检段原样保留**（只重排格式）+ 追加午后段
- 重跑午后 → **替换**午后段，不会在同一份文档里叠出两段

### 7.2 午后只写什么

模型在午后只负责两件事：② 09:30 之后的新动态、⑥ 行动建议。④⑤ 只报计数，不列明细（明细上午已经给过）。

四个确定性收尾：

| 函数 | 作用 |
|---|---|
| `refine_delta()` | 过滤掉 ④⑤ 里重抄的 SKU 明细，只保留计数 |
| `parse_counts()` / `apply_counts()` | 用 `pipeline_alerts` 标题行的数字**覆盖**模型写的数字 |
| `carry_over_actions()` | 承接晨检 ⑥ 的待办，标「（晨检提出，仍未推进）」，不因下午没变化就清空 |
| `PM_DELTA_SOFT_MAX = 1200` | 增量正文超过 1200 字就告警，说明模型可能在重抄基线 |

`carry_over_actions()` 是 2026-10-27 用户反馈后加的：晨检提的待办到了午后整组消失，看起来像「已解决」，其实是下午没新动态。

### 7.3 钉钉消息形态

群里是**两条消息**，不是一条：

```
日报 2026-11-01 · 晨检 09:00
日报 2026-11-01 · 午后更新 14:20 · PM
```

标题里的 `· PM` 是刻意加的机器标记（`pm_tag`），方便事后 grep 区分两段，也方便人一眼看出这是增量不是新报告。

## 8. 推送层（`dingtalk_push.py`）

### 8.1 换行：为什么必须逐行成段

钉钉的 markdown 走**标准 Markdown 语义**：

- 段落内的单个 `\n` 是**软换行**，渲染时被折成空格；
- `•` **不是** Markdown 列表标记（只有 `-` `*` `+` 是），不会自动变成列表项。

所以 `• G598 …\n• G599 …` 这种写法，到群里必然粘成一整行。Web UI 看不出这个问题，因为自定义渲染器用 `<br>` 拼段落内的行。

`to_dingtalk_md()` 的处理：**每个非空行变成独立段落（空行分隔）**，表格行例外（`|` 开头的行之间只留一个换行，否则表头和数据行会被拆散）。

> 别再试图用「给裸行补 `• `」解决——那只解决第一条被折进上一句，不解决两条之间还粘着。

### 8.2 分片

`MAX_MD_CHARS = 3800`（钉钉单条上限 5000，留出标题与 `(i/n)` 后缀余量）。

`split_md()` 只在**段落边界**切；单段超长这种极罕见情况才按行切，仍然**不切半行**。分片后标题带 `(1/2)` 这样的序号。

### 8.3 不再有硬截断

历史问题：推送处曾写死 `answer[:1800]`，2026-10-20 那次把 ⑤ 拦腰砍在「美客多墨西哥 771」，后半段约 900 字全丢。

现在**没有截断**，长文交给 `split_md()` 分片。这条要守住：任何形式的 `[:N]` 都会静默丢内容，而丢的位置恰好是最不重要的尾部——但 ⑤ 的尾部恰恰是超期最久的单子。

### 8.4 发送

- 加签：`HmacSHA256(secret, f"{ts}\n{secret}")` → base64 → urlencode，拼到 webhook 后面
- payload：`{"msgtype": "markdown", "markdown": {"title": ..., "text": "### {title}\n\n{chunk}"}}`
- 成功判定：`errcode == 0`；非 0 返回 `errcode/errmsg`，并提示「若为关键词校验失败，把机器人关键词加进消息标题」
- **频控重试**：`410100`（发送速率过快）/ `130101`（发送太快）按 5s → 15s → 30s 退避重试，最多 3 次。2026-11-04 09:00 只发 1 片也吃到过 410100，旧代码直接判失败，当天群里就没消息
- 任一分片最终失败即返回失败，不继续发后面的片

## 9. 口径常量：改这里，不要改提示词

| 常量 | 值 | 含义 | 影响 |
|---|---|---|---|
| `NEW_SKU_WINDOW_DAYS` | 40 | 新增 SKU 滚动窗口（天） | ③ |
| `SIGN_TARGET_FILM` | 12 | 手机膜签样目标，锚 Part1 取数 | ③ |
| `SIGN_TARGET_SHELL` | 87 | 手机壳签样目标，锚创建时间 | ③ |
| `STALE_CAP_DAYS` | 120 | 超过则归「历史遗留」，不进 TOP | ⑤ |
| `BRIEF_MIN_CHARS` | 100 | 晨检正文下限，不足不推送 | 推送 |
| `PM_MIN_CHARS` | 30 | 午后增量下限 | 推送 |
| `PM_DELTA_SOFT_MAX` | 1200 | 增量超长告警（疑似重抄） | 午后 |
| `MAX_MD_CHARS` | 3800 | 钉钉单条分片上限 | 推送 |

`STALE_CAP_DAYS` 是**单一真源**：`scan_sync_data` 和 `pipeline_alerts` 共用同一个值。90 曾经把 91~120 天的真实挂单错标成历史遗留，所以这个数只在 `plugins/workmain.py` 里定义一次。

改口径只改这些常量，**不需要动提示词，也不需要重新训模型**。

## 10. 已知口径差异（引用时必须标注来源）

| 差异点 | 钉钉线（本文） | 平台事中日报线 |
|---|---|---|
| 环节划分 | Part 编号 + 段级近似 | `segment`（如「素材加工→广告」） |
| 起算锚点 | 提案日期 → 创建时间（候选链） | 同上，但目标天数在数据库 `rule_config` |
| 数据源 | `data/手机膜/手机膜` 同步目录的 Part1–9 | 平台库 + 规则引擎 |

**两套结论不可互相引用。** 在对话里被问到「这个数跟平台报表对不上」时，先确认口径来源，再回答。

另外三条容易踩的：

- ③ 的「一个月」是滚动 40 天，不是自然月。
- ⑤ 的「环节停滞」是段级近似，同一 SKU 会在多环节重复出现。
- ① 只看 `[结论]` 行，数据截至日不推进不代表同步坏了。

## 11. 故障排查

| 现象 | 先看哪里 | 常见原因 |
|---|---|---|
| 群里没消息 | `briefs/<月>/<日期>.md` 是否存在 | 不存在 → 生成阶段就挂了；存在 → 推送阶段失败 |
| ③④⑤ 显示「[系统自动填充]」 | 日志里搜「收尾重渲染」「确定性渲染」 | 修复链重写后没回填（2026-11-04 已补收尾重渲染）；若仍出现，说明 `pipeline_alerts` 取数失败 |
| 生成阶段挂了 | `briefs/task.log` 尾部 | 三次 SSL 中断（`SSLEOFError`）会直接抛 `RuntimeError: LLM流式调用失败` |
| 文件存在但没推 | 日志里的「正文不足 N 字」 | 空壳防线生效，属预期行为，手动重跑即可 |
| 换行又粘成一行 | 是否绕过了 `to_dingtalk_md()` | 直接 `send(原文)` 就会粘；必须走 `send()` 内部转换 |
| 内容被截断 | 有没有人又加了 `[:N]` | 任何硬截断都要删掉，改用分片 |
| 任务面板 Result=1 | 可能是撞锁或空壳 | 撞锁是平台侧问题；空壳看日志 |

手动补跑（不要省略 `--am`，否则 13 点之后会被判成午后）：

```bash
python daily_brief.py --am --push
```

午后补跑用：

```bash
python daily_brief.py --pm --push
```
