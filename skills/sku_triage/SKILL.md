# 超期 SKU 分诊

## 什么时候用
用户问"这么多超期怎么办 / 先催哪个 / 哪些不用管 / 帮我排个优先级"。
**一次处理一批**（≥3 个 SKU）。单个 SKU 的深度复盘用 `review_sku`，不要套本技能。

## 第一步：先剔除「不可动」的，别把力气花在这里
按顺序过一遍，命中任一条就移出待办，不要进排序：

1. **人工登记写了暂缓** —— `inflight_report` 每条 SKU 后面可能带「人工登记: xxx」。
   见到「暂时不弄了」「等 xx 发售」「客户取消」这类，**直接排除**。
   业务上主动搁置的单，催了是添乱，备注优先级高于系统算出的超期天数。
2. **在豁免备查里** —— `inflight_report` 的「豁免备查」段列出的 SKU，业务已主动移出追踪，
   不要再报超期。
3. **历史遗留** —— `pipeline_alerts` 已把 >120 天的单排除并单独计数（"另历史遗留 N 个不列"）。
   不要自己去翻这些老单，也不要建议"清理历史遗留"——那不是当下要处理的事。

剔完剩下的才是真待办。**如果剔完是 0 个，就直说"没有需要处理的"**，不要为了凑数把暂缓单又捡回来。

## 第二步：按「卡在哪」分组，因为催的对象完全不同
`pipeline_alerts` 每条超期都标了 `卡PartN`。Part 之间的责任人不是一批人：

| 卡点 | 在等什么 | 该找谁 |
|---|---|---|
| Part1 产品开发 / Part2 首单下单 | 内部审批与下单动作 | 产品/采购，**内部可推动** |
| Part3 本地仓到货 / Part8 渠道仓到货 | 货到仓 + 到货通知 | 仓储物流 + 供应商，**催内部没用，要问货期** |
| Part4 首次上架 / Part7 最终上架+广告 | 站点上架与广告配置 | 运营/广告，**内部可推动** |
| Part5 渠道仓发货 | 发货动作 | 后勤，**内部可推动** |
| Part6 素材跟进 | 素材产出 | 设计/内容，**内部可推动** |

拿不准某个 Part 到底在等什么，用 `kb_search` 查该环节定义（知识库有逐节点的
「完成标志 / 责任人 / 业务含义」）。**不要凭 Part 编号猜环节内容。**

实测规律（2026-10-29）：当天 12 条超期里 **11 条卡 Part8**。这种时候整体结论是
"堵在到货"，不是"审批效率低"——给的建议必须落到货期和到货通知上。

## 第三步：排序，别按超期天数简单倒序
优先级 = 紧迫度 × 可推动性：

- **先排**：卡内部环节 + 超期天数大 + 近期有硬节点（发售日、促销档期）。
- **后排**：卡外部物流 + 已在途有货件号（`[到货: 渠道 货件号]`）—— 有货件号说明货在动，
  催的是"什么时候到"而不是"为什么不动"。
- **单独一档**：卡了很久但一直没动的（如停滞 100+ 天），多半是死单，
  建议是"确认是否终止"，不是"继续催"。

排序后**最多给 5 条**，每条一行。24 个超期全列出来等于没排。

## 输出结构（固定四段）
    剔除: 因人工登记暂缓 X 个、豁免 Y 个，剩 Z 个待办（一句话，没有就写"无需剔除"）
    分组: 卡 Part8 的 N 个（等到货）、卡 Part2 的 M 个（等审批）…  —— 让读者看到瓶颈在哪
    优先处理: 最多 5 条，每条 "Gxxx 型号 | 卡点 | 超 N 天 | 找谁做什么"
    结论: 一句话说清瓶颈（如"整体堵在渠道仓到货，本周重点是货期，不是审批"）

## 易错点
- **剔除掉的 SKU 不许再出现在「优先处理」里**。实测（2026-10-29）出现过
  「G591 已排除」和「3. G591 … 优先处理」同时写在一份回答里，自相矛盾。
  剔除名单和待办名单互斥，写之前对一遍。
- **一个 SKU 只进一个分组**。同一 SKU 在不同口径下可能既像"产品环节"又像"后勤环节"
  （实测 G599 被同时归到两组），挑它当前真正卡住的那一个，不要重复计数。
- **别把"超期天数大"等同于"最急"**。卡 Part8 超 12 天，可能货已经在路上；
  卡 Part2 超 3 天，可能整个批次卡住。看环节不看天数。
- **别建议"全面催办"**。24 个一起催等于没催，用户要的是"先动哪几个"。
- **别把两套口径混着数**。`pipeline_alerts` 的已超期（全流程线，所有在途单）
  和 `inflight_report` 的超期（平台事中跟踪的在研 SKU）不是一回事，
  分诊用哪个口径要先说清楚，且全程只用一套。
- **分组名不要一半 Part 一半 segment**。Part 口径写"卡 Part8"，segment 口径写
  "卡渠道仓到货"，选了哪套就统一到底。混着写读者会以为是两个不同的 SKU。
- **数据断供时结论要打折**。`pipeline_alerts` 顶部若有 ⚠️ 数据 N 天未同步，
  停滞天数含断供期会虚增，要先说明再给结论。
- 责任人已脱敏，不要补人名；工具没给就不写。

## 验收
- 剔除步骤有交代（哪怕结论是"无需剔除"）
- 分组能看出瓶颈在哪个环节
- 优先处理 ≤5 条，每条有对象和动作
- 结论是一句话判断，不是把表格再念一遍
- 所有数字能指回 `pipeline_alerts` / `inflight_report` 的输出
